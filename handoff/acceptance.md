# 완료 판정과 제출 시연

기계 판독 목록은 acceptance.cases.json의 AC-01~20이다. 이 문서는 그 검사를 수행하는 순서와 제출 시연을 설명한다. 이 팩을 검사했다는 사실을 웹 앱이 완성됐다는 증거로 쓰지 않는다.

이 완료 판정은 이번 프로토타입 범위에만 적용한다. SQLite·S1에서만 Brief 갱신·화면 이동만 수행하는 back·Markdown 출력은 SSAD와 별도로 둔 임시 baseline임을 제출 설명에 밝힌다. 이 설정의 구현·검사 통과를 SSAD의 설계 확정이나 원문 준수의 증거로 사용하지 않는다.

## 최소 제출 가능 상태

source-completion 개정에서는 원문 배경을 보존하고, 기존 API 안에서 승인 Brief 이력·근거 원본 열람, 빈 근거·미검증 표시를 추가로 확인한다. 전체 처리 범위는 SOURCE_COVERAGE.md에 있다.

1. 새 설치에서 API 키 없이 demo 실행 가능.
2. 화면에서 프로젝트를 만들고 여섯 단계를 생성·승인할 수 있음.
3. 승인하지 않은 결과로 다음 단계를 실행하면 서버가 거부함.
4. 직접 편집·코멘트 재생성이 새 버전을 만들고 입력 참조를 보존함.
5. S3 새 승인 후 S4~S6가 오래됨으로 바뀜.
6. 실제 JSON 파일을 업로드하고 원본 지표를 화면과 초안에 연결함.
7. 코드 zip·논문 Markdown·BibTeX 다운로드 가능.
8. demo가 사전 작성 산출물을 사용한다는 사실과 live 검사 여부가 명확함.

live API 키가 있으면 별도의 실제 생성 검사를 수행한다. 키가 없으면 demo 동작과 live 미검사를 구분해 제출한다. 오프라인 fixture 성공을 실제 LLM 품질이나 논문 검색 성능 검증으로 보고하지 않는다.

## 5분 기본 시연

1. APP_MODE=demo로 서버·프런트 시작. 키가 비어 있어도 접속되는지 확인한다.
2. fixtures/project_input.json의 이름·아이디어로 프로젝트를 만든다.
3. S1을 실행하고 Brief를 읽는다. 승인 전 S2가 잠겨 있음을 보여 준다. Brief를 승인한다.
4. S2에서 확인일·출처가 있는 논문 metadata를 보여 주고 승인한다.
5. S3 실험 E1·필수 지표와 계획을 보여 준다. 사용자 코멘트로 재생성하고 새 버전·Decision이 남는지 확인한 뒤 승인한다.
6. S4에서 코드·README와 서버 미실행 표시를 보여 주고 승인한다. zip을 다운로드한다.
7. S5에 fixtures/experiment_result.valid.json을 실제 파일로 업로드한다. 네 지표·환경·수렴 경고를 표시한 뒤 분석을 생성·승인한다.
8. S6 초안의 여섯 섹션과 실험 수치·참고문헌을 확인하고 승인한다. Markdown·BibTeX를 다운로드한다.
9. 앱의 demo 생성 표시와 실제 측정 파일의 출처가 별개임을 설명한다.

## 변경 전파 추가 시연

1. 여섯 단계를 승인한 프로젝트에서 S3 편집을 연다.
2. 계획의 반복 seed 확인 관련 문구를 수정해 저장한다. 저장만으로 승인되지 않았음을 보여 준다.
3. 새 S3 버전을 승인한다.
4. S4·S5·S6가 stale이 되고 과거 결과는 읽을 수 있음을 확인한다.
5. S4를 재생성하고 입력 버전 목록이 새 S3를 가리키는지 보여 준다.
6. S4 재승인 전 S5 실행을 서버가 거부하는지 확인한다.

demo 생성 본문은 사전 작성이므로 임의 연구 주제의 의미 변화를 생성해 낸다고 주장하지 않는다. 입력 연결은 실제 snapshot과 recorder Gateway 테스트로 확인하고, 의미 있는 재생성은 live에서 별도 확인한다.

## 자동화할 중요한 검사

- AC-02: 클라이언트 버튼을 우회한 직접 API 요청도 선행 승인 전 거부.
- AC-03: 새 S3 내용과 코멘트가 다음 Gateway 요청에 실제로 포함됨.
- AC-04~05: 편집 시 새 버전, 승인 시 하위 stale, 과거 버전 불변.
- AC-07: 서버 재시작은 interrupted이며 유료 호출 자동 재실행 없음.
- AC-08: 확인되지 않은 서지나 알 수 없는 cite를 성공 자료로 채택하지 않음.
- AC-09: seed 누락·문자열 수치·NaN·중복 metric·E ID 불일치·다른 Project Run을 거부.
- AC-11: 새 Run 업로드 후에도 과거 초안 수치는 이전 evidence로 렌더링.
- AC-12: 경로가 잘못된 코드 파일을 zip에 넣지 않으며 생성 코드 실행 경로가 없음.
- AC-14: 동일 request_id로 모델 호출·버전·Decision이 중복되지 않음.
- AC-15: timeout·잘림·JSON 보정 상한과 demo/live 경계.

## 원문 정보 보완판의 추가 확인

이 항목은 기존 AC-01~20 안의 확인 내용을 구체화한다. API나 완료 조건 ID를 추가하지 않는다.

- **AC-04 승인 Brief 이력:** S1을 두 번 생성·편집·승인한 뒤 승인 목록에서 두 버전을 연다. 열람 전후 current Brief·Stage 상태·Decision 수가 같고 과거 내용이 수정되지 않아야 한다. 모든 초안이나 diff를 보여 줄 필요는 없다.
- **AC-09 형식 안내:** `sources/ssrd_context.json.external_upload_original.json_example`을 올리면 추가 필수 필드 세 위치에 422가 나와야 한다. 정상 prototype 예시가 어디 있는지 안내한다. 원문 무변환 호환 시험에 통과했다고 적지 않는다.
- **AC-19 가설 대응:** 테스트용 Gateway 또는 직접 편집 검증으로 확인한다. Brief에 H1·H2가 있을 때 H1만 연결한 S3 결과를 거부한다. 모든 가설이 대응하고 `## Ablation 계획`에 계획 또는 해당 없음 사유가 있으면 다음 검사를 진행한다. 고정 demo fixture가 새 H ID 구조를 생성한다고 주장하지 않는다.
- **AC-10 한 Run의 범위:** 선택한 실행이 E1/H1만 다룬다면 H2는 미실행 사유와 inconclusive여야 한다. H2 판정 누락·중복·다른 실험 결과로의 확대는 거부한다.
- **AC-19 근거 열람:** ref/metric/artifact에서 해당 논문·원본 지표 행·특정 산출물 버전을 연다. 빈 evidence_refs에는 ‘근거 없음: 사용자 확인 필요’를 표시한다. 열람 때문에 편집 중 데이터나 연구 상태가 변하지 않아야 한다.
- **AC-08 검증 제외:** 일부 인용 후보 제외 시 대상과 이유를 경고로 표시하고, 본문 허용 목록에는 검증 통과 인용만 남긴다. 모두 제외되면 실패 사유를 보여 준다. S6에도 경고가 보존돼야 한다.
- **AC-18 확인 기록:** LLM_DATA_POLICY.md의 근거 또는 NOT_CHECKED 상태를 기록한다. 앱 기능 시험 PASS와 정책 확인 완료를 구분한다.

정상 JSON 외의 음성 입력은 테스트에서 정상 파일을 복사·수정해 만든다. fixtures/experiment_result.invalid.json은 seed 누락과 잘못된 value 두 위치가 있는 기본 음성 자료다.

## 참조 실험 결과 해석

동봉 결과 파일의 accuracy 두 값은 동일하다. 네 지표의 정확한 값은 JSON을 원본으로 사용한다. 해당 실행에는 학습 미수렴 경고가 있으며, 단일 seed·split이다. ‘차이가 관측되지 않음’과 ‘두 알고리즘이 동등함을 입증함’을 구분한다. fixture의 inconclusive 판단을 결과에 맞는 한계 설명으로 유지한다.
